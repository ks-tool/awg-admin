# ADR 0001: Архитектура VPN-провайдеров и агента

- Статус: принято
- Дата: 2026-11-09

## Контекст

Текущая админка знает структуру WireGuard/AmneziaWG: хранит
`InterfaceConfig`, генерирует peers и ключи, выделяет адреса, формирует
маршруты, NAT и shell-хуки туннелей. Агент применяет уже подготовленную
конфигурацию через WireGuard-специфичный API.

Это мешает поддерживать другие VPN без изменения ядра админки. Требуется
архитектура, в которой любой VPN представлен абстракцией
«приложение–конфигурация», пользовательский интерфейс строится по JSON Schema,
а админка управляет только ресурсами и сетевыми связями между ними.

Проект будет переименован из `awg-admin` в `vpn-admin`. Новые универсальные
контракты сразу не должны содержать название конкретного VPN.

## Решение

Принять модель **Resource → Definition → Reconcile → Status → Action** и
разделить систему на универсальный control plane, agent-core и VPN-провайдеры.

```text
vpn-admin
├── Server, User, Resource, Link
├── Provider/Schema registry
├── RJSF renderer
└── Link coordinator
          │
          ▼
vpn-agent
├── generic resource API
├── desired-state storage
├── reconcile queue + Watch/resync
├── host metrics
└── provider runtime
          │
          ├── AWG provider
          ├── OpenVPN provider
          └── другие провайдеры
```

Админка не интерпретирует поля конкретного VPN. В частности, её универсальное
ядро не знает о `PrivateKey`, `AllowedIPs`, AmneziaWG-параметрах, `ip rule`,
`iptables` и `MASQUERADE`.

## Термины и границы

### vpn-admin

Отвечает за:

- серверы и параметры подключения к агентам;
- глобальных пользователей;
- хранение ресурсов как универсальных JSON-документов;
- кеширование описаний провайдеров и схем;
- построение форм через RJSF;
- топологию, проверку допустимости и цикличности связей;
- координацию распределённого создания и удаления `Link`;
- отображение универсального состояния ресурсов и агентов.

### vpn-agent

Отвечает за:

- версионированный API и discovery;
- регистрацию провайдеров;
- локальное хранение desired state;
- структурную и семантическую валидацию;
- идемпотентный reconcile и повторные попытки;
- фактическое состояние ресурсов;
- выполнение объявленных действий;
- локальные секреты, host-метрики и наблюдаемость.

### VPN-провайдер

Провайдер — единица развёртывания и управления конкретным VPN. Он:

- описывает свои ресурсы, схемы, порты и действия;
- преобразует `spec` в конфигурацию VPN и ОС;
- выполняет reconcile и удаление;
- сообщает фактическое состояние и VPN-специфичные метрики;
- участвует в построении совместимых связей;
- генерирует клиентские конфигурации через действия.

По умолчанию на сервере работает один агент с несколькими встроенными
провайдерами. Отдельный процесс или отдельный агент для провайдера допускается
и использует тот же протокол. Плагины Go `.so` не используются из-за
зависимости от версии Go, зависимостей и ОС.

Отдельный процесс изолирует сбой, но не является security sandbox: провайдер,
работающий с сетевыми настройками хоста, считается доверенным кодом.

## Использование существующих проектов

### pack

Из `pack` разрешено напрямую использовать SDK:

- `pack/sdk/packschema.Reflect` — генерация JSON Schema из Go-структур и
  применение `SetDefaults`;
- `pack/sdk/schema.Compile` — компиляция и структурная валидация схем;
- существующие типы и соглашения `SecretRef`;
- механизмы документации и схем параметров действий, где они подходят без
  переноса deployment-семантики pack.

VPN-провайдер не обязан реализовывать полный `sdk.Pack` и `PackRoot`.

Если используются существующие pack-типы, их `x-pack-*` сохраняются. Новые
расширения VPN-контракта называются `x-vpn-*`; форк SDK с механическим
переименованием расширений не создаётся.

### cloud-controller

`cloud-controller` является только архитектурным референсом. Его код,
зависимости и Kubernetes-типы не импортируются и не копируются.

Допускается самостоятельно реализовать идеи:

- динамической регистрации схем;
- универсальных ресурсов;
- объявления действий через API;
- асинхронного reconcile;
- Watch в сочетании с периодическим resync;
- состояния через `Ready`, причину и сообщение об ошибке.

Kubernetes API-конвенции, `unstructured.Unstructured`, Postgres, HA,
dynamic router и другие детали реализации в проект не переносятся.

## Discovery и схемы

После подключения админка сама запрашивает описание у агента. Это работает
одинаково через SSH-туннель и прямое mTLS-подключение и не требует от агента
доступа к админке.

Минимальный API:

```text
GET    /v1/manifest
GET    /v1/providers/{provider}/schema
GET    /v1/providers/{provider}/resources
PUT    /v1/providers/{provider}/resources/{kind}/{name}
DELETE /v1/providers/{provider}/resources/{kind}/{name}
GET    /v1/providers/{provider}/resources/{kind}/{name}/status
POST   /v1/providers/{provider}/resources/{kind}/{name}/actions/{action}
GET    /v1/events
```

Манифест содержит:

- `protocolVersion` и стабильный `agentId`;
- имя и версию каждого провайдера;
- поддерживаемые `apiVersion` и `kind`;
- описание портов и совместимых `LinkKind`;
- действия и схемы их аргументов;
- версию или хеш схемы для инвалидации кеша.

Для каждого ресурса передаются `specSchema` и отдельная `uiSchema`. JSON Schema
используется и для RJSF, и для обязательной валидации на агенте. Доверять только
проверке в браузере нельзя.

Схема не заменяет семантическую валидацию: занятость порта, пересечение
подсетей, доступность backend и совместимость ресурсов проверяет провайдер.
Динамические списки значений запрашиваются через API, а не зашиваются в
статическую схему.

## Модель ресурсов

Универсальная запись ресурса содержит как минимум:

```json
{
  "id": "stable-uuid",
  "serverId": "server-uuid",
  "apiVersion": "awg/v1alpha1",
  "kind": "Interface",
  "name": "awg0",
  "generation": 1,
  "spec": {},
  "status": {}
}
```

`spec` хранится админкой без интерпретации, например как `json.RawMessage`.
Идентичность ресурса не зависит от имени сетевого интерфейса ОС.

VPN Interface и VPN Peer — отдельные ресурсы. Peer ссылается на Interface и,
когда применимо, на глобального пользователя:

```json
{
  "apiVersion": "awg/v1alpha1",
  "kind": "Peer",
  "spec": {
    "interfaceRef": "office",
    "userRef": "alice"
  }
}
```

Это позволяет независимо настраивать, отзывать и диагностировать доступ без
пересборки всего интерфейса. Глобальный пользователь админки не заменяется
VPN-специфичным peer.

## Reconcile и состояние

Изменение ресурса проходит последовательность:

```text
сохранить desired state
→ увеличить generation
→ Validate
→ Reconcile
→ записать observedGeneration и status
→ повторить с backoff при временной ошибке
```

Требования:

- reconcile идемпотентен;
- агент повторно применяет ресурсы после перезапуска;
- периодический resync компенсирует пропущенные события;
- ошибка применения не удаляет desired state;
- повторная доставка той же ревизии безопасна;
- одновременные изменения одного ресурса сериализуются;
- удаление учитывает ссылающиеся ресурсы и связи.

Универсальный `status` включает `observedGeneration`, `phase` и `conditions`.
Условие содержит как минимум `type`, `status`, `reason` и `message`. Провайдер
может добавлять свои read-only поля, не изменяя универсальный конверт.

Админка различает недоступность агента, ожидание/рассинхронизацию и готовность
ресурса. Host-метрики остаются обязанностью agent-core, VPN-метрики —
провайдера.

## Действия вместо произвольных хуков

Операции, которые нельзя выразить изменением `spec`, объявляются как действия:
`renderClientConfig`, `rotateKeys`, `restart`, `revoke` и другие.

Действие описывает:

- стабильное имя и отображаемый заголовок;
- JSON Schema аргументов для RJSF;
- тип результата: JSON, файл или асинхронная задача;
- таймаут;
- признаки изменяющей и требующей подтверждения операции.

Команда действия реализована внутри провайдера. Админка не передаёт
произвольный shell для выполнения на сервере.

Существующие `PreUp`, `PostUp`, `PreDown`, `PostDown`, маршруты и NAT становятся
внутренней reconcile-логикой AWG-провайдера, а не редактируемой частью
универсального API.

## Link-протокол

Связь между ресурсами — самостоятельный `Link`, а не поле одного из интерфейсов.
Он содержит стабильный UUID, ссылки на ресурсы и порты, направление/роли,
`LinkKind`, параметры и состояние.

Провайдер объявляет совместимость портов. Наличие стрелки в редакторе не делает
произвольную пару VPN технически совместимой.

Создание распределённой связи выполняется в две фазы:

```text
PrepareLink на обеих сторонах
→ получить LinkOffer каждой стороны
→ обменять offers через vpn-admin
→ CommitLink на обеих сторонах
→ наблюдать локальные статусы
→ перевести Link в Ready после готовности обеих сторон
```

`LinkOffer` непрозрачен для админки. Например, для AWG он может содержать
публичный ключ, endpoint и параметры протокола. Провайдер сам создаёт peers,
маршруты, NAT и остальную локальную конфигурацию.

Распределённая атомарная транзакция не предполагается. Link использует состояния
`Pending`, `Preparing`, `Ready`, `Degraded` и поддерживает повторный
Prepare/Commit. Частично применённая связь диагностируется и доводится повторным
reconcile.

Удаление связи идемпотентно и удаляет только артефакты этой связи. Базовые
интерфейсы и пользовательские peers сохраняются.

## Секреты

Новые приватные ключи генерируются на агенте. В `status` попадают только
публичные значения. Приватные ключи не включаются в RJSF, события, логи и
обычные ответы ресурсов.

Клиентская конфигурация выдаётся через действие провайдера. Секреты передаются
по ссылкам `SecretRef`, когда их значение не требуется непосредственно
провайдеру.

## Хранилище и миграция

BoltDB сохраняется как хранилище `vpn-admin`, но текущий формат записей не
сохраняется. Требуется одноразовая версионированная миграция данных. Отказ от
обратной совместимости API не означает отказ от сохранения пользовательских
данных.

Без структурных изменений сохраняются:

- UUID и параметры серверов, включая Location, SSH и TLS;
- глобальные пользователи и учётные данные администратора;
- источники агентов;
- координаты и расположение элементов топологии.

Преобразуются:

| Текущие данные | Новое представление |
|---|---|
| `models.Interface` | `awg/v1alpha1, Kind=Interface` |
| `Interface.Tunnel` | отдельный `Link` |
| пользовательские `models.Peer` | `awg/v1alpha1, Kind=Peer` с `interfaceRef` и `userRef` |
| `InSync`, `LastSyncError` | универсальные `status` и `conditions` |
| топологические `Connections` | `Link`, если связь выражает VPN-туннель |

Существующие UUID интерфейсов сохраняются. Добавляются buckets `resources`,
`links`, `providers`, `meta` и при необходимости отдельные индексы. Buckets
`servers`, `users`, `auth`, `agent_sources` могут остаться.

В `meta.schemaVersion` записывается версия формата. Миграции последовательны и
явно тестируются на копиях прежних БД.

Порядок миграции:

```text
остановить обычную работу с БД
→ создать резервную копию через существующий Backup
→ проверить schemaVersion
→ преобразовать данные одной BoltDB-транзакцией
→ записать новую schemaVersion
→ запустить приложение
```

Миграция не подключается к агентам, не запускает reconcile и не изменяет
работающие VPN. Старые версии приложения с новой БД не поддерживаются;
откат выполняется восстановлением резервной копии. Dual-write между старой и
новой моделями не вводится.

Существующие ключи при структурной миграции не ротируются и не удаляются. Их
перенос в локальное хранилище агента выполняется отдельно. Только после
подтверждения агента админка удаляет свою прежнюю копию. Если агент недоступен,
ключ остаётся в прежнем хранилище с состоянием `SecretMigrationPending`.

Локальные `~/.awg-agent/*.json` на первом этапе продолжает читать AWG-провайдер.
Миграция локального хранилища агента требуется только при переходе на
универсальное ресурсное хранилище и оформляется отдельно.

## Порядок внедрения

1. Выделить нейтральные контракты Resource, Definition, Status, Action и Link,
   не импортирующие AWG-модели.
2. Реализовать минимальный resource API и RJSF-путь в админке.
3. Перенести AWG в первый встроенный провайдер, генерирующий схемы через pack
   SDK, без изменения сетевого поведения.
4. Выполнить миграцию BoltDB и представить существующие interfaces/peers как
   ресурсы.
5. Перенести генерацию клиентских конфигураций в действия.
6. Перенести построение туннелей в PrepareLink/CommitLink.
7. Добавить внешние провайдеры в отдельных процессах после стабилизации
   контракта.
8. При необходимости использовать OCI для распространения провайдеров; runtime
   discovery всё равно выполняется у работающего агента.

Первый вертикальный срез: AWG Interface + Peer + Link. Критерий успеха —
отсутствие AWG-специфичных условий в универсальном ядре админки.

## Последствия

Положительные:

- новые VPN добавляются провайдерами без изменения топологии и RJSF-ядра;
- админка перестаёт быть вторым генератором VPN-конфигурации;
- агент автономно восстанавливает desired state;
- состояние и ошибки становятся единообразными;
- существующие данные сохраняются через явную миграцию.

Стоимость:

- требуется миграция БД и перенос AWG-логики;
- Link требует отдельного распределённого протокола;
- универсальные схемы не отменяют семантическую валидацию;
- внешние провайдеры остаются доверенным привилегированным кодом.

Полный Kubernetes-compatible API, собственный CRD-сервер и универсальная
распределённая транзакция в объём решения не входят.
