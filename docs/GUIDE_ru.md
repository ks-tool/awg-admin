## Установка и запуск

VPN Admin работает в двух режимах с общей базой, бизнес-логикой и frontend.

### Desktop-приложение

Готовые сборки публикуются на странице [Releases](../../../releases):

- **Windows** — `vpn-admin-amd64-installer_<версия>.exe` (NSIS) или переносимый `vpn-admin_<версия>.exe`;
- **macOS** — универсальный `vpn-admin_<версия>.dmg` для Intel и Apple Silicon;
- **Linux** — `vpn-admin_<версия>`; требуются `libgtk-3` и `libwebkit2gtk-4.1`.

Desktop-приложение не открывает сетевой HTTP API и не требует входа. macOS-сборка имеет ad-hoc подпись, но не нотаризована.
При первом запуске выберите **Open** в контекстном меню Finder либо снимите карантин:

```sh
xattr -cr "/Applications/VPN Admin.app"
```

### Standalone-сервер

Запуск локального бинарника:

```sh
./vpn-admin
```

Запуск официального контейнера:

```sh
docker run -d --name vpn-admin \
  -p 8080:8080 \
  -v vpn-admin-data:/data \
  ghcr.io/ks-tool/vpn-admin:latest
```

По умолчанию HTTP-сервер слушает `:8080`. При первой инициализации базы создаётся один администратор:

- логин: `admin`;
- пароль: `admin`.

Сразу смените учётные данные в **Settings**. Соответствующий API использует `POST /auth/change-credentials`, а не метод PUT
из старых инструкций. Аутентификация нужна только в standalone-режиме.

### Конфигурация и каталоги

| Переменная | Назначение |
|---|---|
| `VPN_ADMIN_ADDR` | Адрес standalone HTTP-сервера; по умолчанию `:8080`. |
| `VPN_ADMIN_TLS_CERT` / `VPN_ADMIN_TLS_KEY` | Статический TLS-сертификат и закрытый ключ для HTTPS. |
| `VPN_ADMIN_AUTOCERT_DOMAINS` | Домены Let's Encrypt через запятую; несовместимо со статическим сертификатом, требует доступный порт 80. |
| `VPN_ADMIN_AUTOCERT_CACHE_DIR` | Кэш ACME; по умолчанию `~/.vpn-admin/acme`. |
| `VPN_ADMIN_PLUGINS_DIR` | Каталог manifest-файлов внешних deployment plugins; по умолчанию `~/.vpn-admin/plugins`. |

Прежние переменные с префиксом `AWG_ADMIN_` принимаются как fallback. Основные пути:

| Путь | Содержимое |
|---|---|
| `~/.vpn-admin/db` | Вся административная BoltDB. |
| `~/.vpn-admin/acme` | Сертификаты autocert standalone-интерфейса. |
| `~/.vpn-admin/plugins` | `plugin.json` и исполняемые файлы deployment plugins. |
| `~/.vpn-admin/cache` | Pack state, target, кэши релизов и `datacenter-atlas.json`. |

В Docker `HOME=/data`, поэтому volume `/data` сохраняет базу и рабочие каталоги. Не храните единственную копию базы только во
временном контейнере.

## Архитектура v2

В текущей модели есть серверы, сетевые интерфейсы, VPN-сервисы, ресурсы провайдеров и направленные связи. Важно различать два
независимых механизма расширения.

### Агент и провайдеры

`vpn-agent` работает на управляемом хосте и не знает специфику Xray, Hysteria, AWG или другого протокола. Он:

- хранит желаемые `Resource` и регистрации провайдеров в `VPN_AGENT_DB`;
- запускает каждый провайдер дочерним процессом, перезапускает после сбоя и останавливает при shutdown;
- получает manifest и JSON-схемы через provider API;
- reconciles resources и участвует в `prepare`/`commit`/`delete` для links;
- предоставляет host info, системные метрики и ICMP-задержку.

Провайдер — отдельный необязательный компонент. Его собственный pack описывает пакеты ОС, переменные окружения, файлы,
регистрацию и зависимости. Systemd запускает только `vpn-agent`; отдельных provider unit-файлов нет.

При `discover: true` агент читает определения через `GET /v1/manifest` провайдера. Статическая регистрация может содержать
определения непосредственно. Провайдеры обычно слушают loopback; удалённые регистрации должны использовать mTLS.

AWG-провайдер выбирает kernel backend при доступном `modinfo amneziawg` или `modinfo wireguard`, иначе использует
`amneziawg-go`. Опция установки `userspace`, флаг `--userspace` или `VPN_PROVIDER_AWG_USERSPACE=true` принудительно выбирают
userspace.

Основные настройки агента задаются environment и одноимёнными flags (flags имеют приоритет):

| Переменная | Назначение |
|---|---|
| `VPN_AGENT_ADDR` | HTTP listen address; по умолчанию `127.0.0.1:8080`. |
| `VPN_AGENT_DB` | Каталог resources, providers.d и истории; по умолчанию `~/.vpn-agent`, в pack — `/var/lib/vpn-agent`. |
| `VPN_AGENT_TLS_CERT` / `VPN_AGENT_TLS_KEY` / `VPN_AGENT_TLS_CLIENT_CA` | Все три файла вместе включают mTLS. |
| `VPN_AGENT_LEGACY_PROXY` | Loopback URL AWG-провайдера для legacy API и интерфейсных метрик; в pack — `http://127.0.0.1:9091`. |
| `VPN_AGENT_METRICS_INTERVAL` | Интервал системных метрик и ICMP-проб; по умолчанию `45s`. |
| `VPN_AGENT_LOG_LEVEL` | Уровень логирования; по умолчанию `info`. |

Полный список flags доступен через `vpn-agent --help`. AWG-провайдер использует настройки с префиксом `VPN_PROVIDER_AWG_`, включая
`DB`, `ADDR` и `METRICS_INTERVAL`.

### Плагины VPN-сервисов

Deployment plugin рассматривает VPN-сервис как абстракцию **приложение + конфигурация**. Admin передаёт ему сервис, сервер,
привязанный интерфейс и connections этого интерфейса. Плагин отвечает за `apply`, `delete`, `status` и пользователей сервиса.
Ядро не интерпретирует содержимое `service.config`.

Plugin предоставляет отдельные JSON Schema для конфигурации приложения и одного пользователя; RJSF строит по ним формы. Это не
тот же контракт, что agent provider manifest: plugin вызывается из admin и управляет сервисом целиком, provider работает рядом
с агентом и владеет конкретными ресурсами.

### Желаемое состояние и синхронизация

`~/.vpn-admin/db` — источник истины для инвентаря, пользователей, топологии, OCI-источников и связей. Агент дополнительно хранит
собственную копию желаемых ресурсов, поэтому утверждение «агент ничего не сохраняет» относится только к старой v1-модели.

Для перенесённого AWG-инвентаря изменение сначала записывается локально, затем передаётся агенту best-effort. Ошибка отображается
в `inSync`/`lastSyncError` и не откатывает запись. Повторная передача происходит после развёртывания и восстановления
SSH-туннеля; standalone API также предоставляет `POST /servers/:id/sync`.

Для generic provider resource `PUT` сохраняет desired state и запускает reconcile. Интерфейс повторно читает ресурсы и показывает
фактические `generation`, `observedGeneration`, phase и conditions. Ошибка провайдера не удаляет желаемую конфигурацию.

## Рабочее пространство

Кнопки в правом верхнем углу переключают четыре представления:

- **Map** — география, статусы и туннели;
- **Network Graph** — интерфейсы и направленные связи;
- **Users** — глобальные пользователи AWG и их пиры;
- **Settings** — язык, backup, журналы desktop и безопасность standalone.

Кнопка **+** добавляет сервер на Map/Graph или пользователя на Users. Отдельных страниц Servers, Dashboard и Tunnels из v1 в
текущем рабочем пространстве нет.

## Серверы и карта

### Добавление сервера

В модальном окне указываются имя, SSH host/port/user, аутентификация, адрес агента, описание, Location и ноль или больше
интерфейсов. Создание записи не означает успешное подключение: ошибки SSH проявляются при последующих операциях.

Сервер, созданный этой формой, принадлежит текущему agent-based inventory и автоматически проецируется в Topology с сохранением
UUID. Его интерфейсы появляются в Network Graph. Абстрактные topology-only серверы без agent inventory также поддерживает API,
но для них вкладки Agent и Providers отключены.

### SSH и mTLS

Поддерживаются:

- путь к приватному ключу на машине с vpn-admin;
- содержимое загруженного PEM-ключа, сохранённое в базе; оно имеет приоритет над путём;
- SSH-пароль для обычных подключений, но **не для pack host target**.

Passphrase защищённого ключа запрашивается при первом подключении и хранится только в памяти процесса. Опция «использовать для
всех» применяет её как fallback к другим серверам. SSH host keys сейчас не сверяются с `known_hosts`.

По умолчанию агент слушает `127.0.0.1:8080`, а admin обращается через долгоживущий SSH-туннель. При включённом **Generate TLS**
создаются CA, сертификат сервера и клиентский сертификат; дальше используется прямой mTLS к адресу агента. Материал TLS хранится
в административной базе и передаётся агенту при pack deployment.

### Location и координаты

Если заполнен **Location**, vpn-admin ищет город в Data Center Atlas. Поддерживается уточнение `Город, Страна`; поиск
нормализует регистр и кириллическую транслитерацию. При нескольких совпадениях без уточнения страны используется первая
подходящая запись датасета.
Датасет `sites.json` скачивается из `https://kiankyars.github.io/datacenter-atlas/api/v1/sites.json` и кэшируется в
`~/.vpn-admin/cache/datacenter-atlas.json` на 24 часа. При ошибке обновления используется старый кэш.

Ручные широта и долгота доступны **только при пустом Location**. Указание Location отключает эти поля; изменение Location
сбрасывает прежние координаты и запускает новый поиск. Сервер без результата остаётся в списке **Unlocated servers**, где видна
ошибка геокодирования.

Карта показывает материки, кроме Антарктиды, и вписывает их в окно. Доступны масштаб 100–600%, сброс масштаба и перетаскивание
при увеличении. Совпадающие точки объединяются в кластеры; клик по кластеру раскрывает входящие серверы.

### Статусы и управление сервером

Для agent-based сервера цвет берётся из проверки агента:

- **зелёный** — агент доступен и мигрированные ресурсы приняты;
- **жёлтый** — переходное, degraded или unmanaged состояние;
- **красный** — соединение или агент недоступны.

Для topology-only сервера используется худший статус его VPN-сервисов: running — зелёный, error — красный, остальное — жёлтый.
Tooltip содержит адрес, координаты, статус агента и сервисы. Нативный SVG alt-tooltip поверх него не используется.

Клик по точке открывает **Manage panel** с вкладками:

- **Interfaces** — специализированный AWG-редактор;
- **Providers** — generic resources и действия;
- **Agent** — установка агента и провайдеров;
- **Metrics** — система и пиры;
- **Information** — SSH, TLS и метаданные.

Agent и Providers доступны только для agent-based inventory.

## Network Graph и туннели

Graph отображает узлы интерфейсов, имя сервера/адрес, CIDR и привязанный сервис. Узлы можно перетаскивать; координаты сохраняются.
Есть minimap, zoom и pan.

### Создание и удаление связи

Перетащите стрелку от source handle одного интерфейса к target handle другого и подтвердите маршрут кнопкой **Создать**. Нельзя
создать самосоединение, дубликат или цикл.

Для двух agent-based AWG-интерфейсов создаётся **provider link**:

1. Admin проверяет `linkKinds` и `remotePorts` в manifest обеих сторон.
2. Оба агента выполняют `prepare` и обмениваются offers через admin.
3. Обе стороны выполняют `commit`; только затем link получает `Ready`.
4. При ошибке link сохраняется как `Degraded` с condition, а не исчезает молча.

Если хотя бы один endpoint topology-only, создаётся абстрактная `NetworkConnection`. Она сохраняется в Topology и передаётся
плагину при следующем **Apply** сервиса; сама по себе она не вызывает agent provider API.

Выделенную стрелку можно удалить клавишей **Delete** или **Backspace** с подтверждением. Удаление provider link удаляет только
созданных tunnel peers и служебные hooks/маршруты этой связи. Интерфейс и пользовательские пиры сохраняются.

### Цепочки из нескольких нод

Provider links не ограничены старым мастером «ровно два интерфейса». Можно построить `A → B → C → D → E`; один промежуточный
интерфейс может одновременно быть target предыдущего и source следующего link.

Для AWG source получает peer к следующей ноде, `AllowedIPs = 0.0.0.0/0` и отдельную policy-routing таблицу. Target получает
обратный peer и правила marking/NAT. На промежуточной ноде обе роли применяются независимо к соответствующим связям. Правила
имеют производные от link ID таблицы и marks, а не общий глобальный номер.

Firewall хоста настраивается отдельно через pack/host target; поддерживаются firewalld, ufw и iptables. VPN Admin не требует
вручную повторять команды из примеров v1.

### Перемещение туннеля

Существующий маршрут можно изменить без ручного удаления и повторного создания:

1. Выделите стрелку и нажмите `m`.
2. Перетащите начало, чтобы заменить **source**, или конец, чтобы заменить **target**.
3. Проверьте старый и новый маршруты и нажмите **Создать**.

`Esc` выходит из режима перемещения; **Отмена** в модальном окне не меняет конфигурацию. Проверки дубликатов, совместимости и
циклов выполняются с учётом остальных связей.

Для provider link admin сначала создаёт replacement через агенты новых нод, затем удаляет прежний link. Если создание не удалось,
выполняется попытка очистки replacement с сохранением прежнего туннеля. Если не удалось удалить прежний, выполняется попытка
отката replacement. Ошибки cleanup/rollback выводятся, поскольку часть состояния могла остаться на нодах. Возможен краткий
перерыв трафика.

Для абстрактной `NetworkConnection` изменение атомарно записывается в Topology. Его фактическое применение зависит от plugin
`Apply` соответствующего сервиса.

## Установка агента и провайдеров

### OCI registry и локальный бинарник

В **Manage panel → Agent** доступны:

- **OCI release** — источник, repository и tag; список тегов загружается из registry и сортируется по semver;
- **Local binary** — путь к локальному `vpn-agent`; в desktop есть файловый диалог, в standalone путь относится к машине сервера
  админки, а не к компьютеру с браузером.

При первой инициализации базы добавляется `GitHub Container Registry — oci://ghcr.io`. Это одноразовая операция по marker в
`meta`, включая миграцию v1→v2: после удаления источник не появляется снова.

Через **Add registry** можно сохранить частный registry: имя, host:port без repository path, username/password и опцию plain HTTP.
Пароль хранится в BoltDB, не возвращается в list/get API и не показывается в форме повторно; пустое поле при редактировании
сохраняет прежний пароль. HTTPS используется по умолчанию, plain HTTP следует включать только в доверенной сети.

### Независимая установка провайдеров

Сначала установите агента. Затем в **Installed providers** нажмите **+**, выберите каталог, провайдера и версию. Для официального
GHCR список провайдеров определяется по release tags `providers/<name>/v*` репозитория `ks-tool/vpn-agent`; частный registry
должен поддерживать OCI `_catalog` для автоматического списка. Repository и имя также можно ввести вручную.

Каждый провайдер устанавливается собственным `pack apply`, отдельно от агента. Для AWG доступна provider-specific опция
`{"userspace": true}`; ядро не навязывает эту опцию другим провайдерам. Кнопка **−** удаляет регистрацию провайдера через его
pack. Установленные имя и версия читаются из `/v1/manifest`.

Операции асинхронны: UI опрашивает deployment status и показывает текущий шаг или ошибку. После успеха admin синхронизирует
инвентарь сервера. Агент сам не устанавливает провайдеры и не вызывает pack.

### Требования к управляемому хосту

Host target поддерживает **Debian и Fedora**, архитектуры **amd64 и arm64**. Для развёртывания нужны:

- SSH-аутентификация ключом; password-only SSH для pack не поддерживается;
- root либо non-root пользователь с **passwordless sudo**;
- сетевой доступ admin к SSH и управляемого хоста к OCI registry через временный proxy;
- для AWG userspace — `/dev/net/tun` и `CAP_NET_ADMIN`;
- для AWG kernel — подходящий модуль `amneziawg` или `wireguard`; для обфускации AmneziaWG 2.0 нужен совместимый модуль.

Admin вызывает `pack apply` как Go-библиотеку, без внешнего `pack` CLI. Target `host` скачивается автоматически. На время
операции target открывает отдельное SSH-соединение и поднимает временные host agent и OCI-proxy на loopback. Локальный бинарник
при self-deploy передаётся как pack content, без скачивания из OCI.

### Firewall и обновление с awg-agent

AWG pack включает `net.ipv4.ip_forward=1`. При установке провайдера и после успешного изменения AWG-интерфейса host target
добавляет входящее разрешение **по имени интерфейса**, например `i:awg0`, через доступный firewall backend. Отдельный lightweight
firewall pack не скачивает провайдера повторно и не перезапускает агента. Не нужно вручную ставить iptables ради этих правил.

При установке нового `vpn-agent` pack сначала останавливает legacy `awg-agent.service`. После успешного запуска и readiness нового
агента старый unit и `/usr/local/bin/awg-agent` удаляются. Поэтому обновление выполняется из Manage panel, без ручных команд на
сервере.

## Ресурсы провайдеров

Вкладка **Providers** объединяет ресурсы всех провайдеров из manifest агента. Для каждого ресурса показываются provider/kind,
phase, observed generation и condition. Цвет индикатора: Ready — зелёный, Degraded — красный, Pending/Deleting — жёлтый.

Кнопка **+** открывает выбор provider и kind. Поле `spec` строится через RJSF из `specSchema`/`uiSchema`; имя и тип существующего
ресурса неизменны. Если схема содержит boolean `disabled`, доступно включение/выключение без удаления.

Manifest может объявлять действия с собственной схемой аргументов. VPN Admin поддерживает:

- JSON-результат;
- файл с именем и media type, который можно скачать;
- asynchronous result с `taskId`;
- `mutating` и `requiresConfirmation`.

AWG предоставляет ресурсы `Interface` и `Peer`, включая render client config, rotate/revoke и secret import для миграции.
Generic editor не заменяет валидацию провайдера: семантические ошибки возвращаются через status/conditions.

## AWG-интерфейсы, пользователи и пиры

### Специализированный редактор интерфейсов

Для agent-based AWG inventory сохранён специализированный редактор на вкладке **Interfaces**. Он дополняет generic Providers UI.
Основные поля: имя, CIDR, DNS клиентов, listen port, приватный ключ, активность и параметры AmneziaWG.

- Пустой адрес при создании выделяет первый хост следующей свободной `/24` из `172.23.0.0/16`.
- Пустой приватный ключ генерируется автоматически.
- Имя, порт и пересечение подсетей проверяются относительно других интерфейсов сервера.
- Отключение сохраняет конфигурацию, но опускает интерфейс.
- Обычный WireGuard получается при снятии флажка Amnezia; параметры `Jc/Jmin/Jmax`, `S1–S4`, `H1–H4`, `I1–I5` иначе задают
  обфускацию.
- **Force replace peers** применяет `ReplacePeers=true` и сбрасывает активные сессии интерфейса.

Интерфейс, занятый tunnel metadata, нельзя редактировать или удалять из специализированного редактора, пока не удалена связь.
Удаление свободного интерфейса каскадно удаляет его пиры и требует дополнительного подтверждения при их наличии.

Hook-команды `PreUp`, `PostUp`, `PreDown`, `PostDown` выполняются с привилегиями агента; `%i` заменяется именем интерфейса.
AWG link использует служебные hooks для policy routing и NAT и удаляет только свои команды.

### Пользователи и клиентские пиры

Представление **Users** управляет глобальными владельцами AWG-пиров. Пользователь имеет имя, описание и состояние enabled/disabled;
его пиры могут находиться на разных серверах. Это отдельная модель от пользователей конкретного plugin VPN-сервиса.

При создании пира выбираются сервер и интерфейс. Поддерживаются имя устройства, Allowed IPs, endpoint, DNS, приватный ключ и
preshared key. Пустой адрес назначается из свободного пула интерфейса, пустой ключ генерируется. Хост `/32` должен принадлежать
подсети и быть уникальным; более широкий CIDR допускается для site-to-site маршрутов.

Для пира доступны клиентский `.conf` и QR-код. В desktop файлы сохраняются нативным диалогом, в standalone скачиваются браузером.
Пир можно деактивировать без потери ключей или переместить на другой интерфейс: ключи, имя, DNS и PSK сохраняются, адрес
сохраняется, если подходит новой подсети и свободен; иначе назначается новый. Оба интерфейса синхронизируются.

### Импорт wg-quick / awg-quick

Живой интерфейс, созданный вне агента, появляется в Interfaces как **Not managed** и read-only. **Import…** читает
`/etc/amnezia/amneziawg/<имя>.conf`, затем `/etc/wireguard/<имя>.conf`.

Перед импортом выполните **Preview**: он показывает интерфейс, пользователей/пиров, собственные и сгенерированные hooks и
предупреждения, ничего не изменяя. Peer map позволяет сопоставить приватные ключи существующих клиентов пользователям; без него
пиры сохраняются, но admin не сможет восстановить их приватные ключи для новых клиентских конфигов.

Импорт сохраняет инвентарь в BoltDB и передаёт его агенту. Живой kernel link подхватывается на месте; userspace не может принять
чужой kernel link — сначала опустите его и повторите Sync. После перехода отключите `wg-quick@<имя>` или `awg-quick@<имя>`, чтобы
у интерфейса остался один владелец. Заранее отключите `SaveConfig`, иначе остановка wg-quick перезапишет файл.

`DNS`, `Table`, `AllowedIPs`, hooks и ограничения конфигурации проверяются preview. Неидемпотентные hooks требуют чистого перехода
через `wg-quick down`; не следует без проверки применять их поверх уже настроенных правил.

## Модель VPN-сервисов и внешние плагины

В Topology сервис хранит `serverId`, необязательный `interfaceId`, `pluginId`, имя, opaque `config`, status и message. Сохранение
конфигурации переводит сервис в `pending`; **Apply** вызывает плагин и сохраняет возвращённый статус. Пользователи сервиса
создаются, читаются, изменяются и удаляются через тот же плагин.

Встроенный plugin `vpn-agent` управляет AWG-интерфейсом через уже существующий agent HTTP URL. Он не устанавливает агент: установка
выполняется отдельно на вкладке Agent.

Внешний plugin — доверенный исполняемый файл. В `~/.vpn-admin/plugins/<id>.json` указывается:

```json
{
  "id": "example",
  "executable": "example-plugin"
}
```

Относительный executable разрешается от каталога plugins. Для каждой операции admin запускает процесс заново, передаёт один JSON
request в stdin и ожидает один JSON response в stdout. Версия process protocol — `1`; поддерживаются действия:

```text
describe
apply
delete
status
users.list
users.create
users.update
users.delete
```

`describe` возвращает descriptor с `configSchema`, `userSchema`, необязательным `uiSchema`, именем и версией. Другие вызовы
получают `deployment` с сервисом, сервером, интерфейсом и connections. Ошибка возвращается в поле `error` либо через stderr и
ненулевой exit code. Таймаут вызова — 30 секунд. Go `.so` plugins не поддерживаются, поэтому язык реализации произвольный.

> **Ограничение текущего frontend.** Модель, HTTP API, RJSF-формы и inspector сервисов реализованы, но кнопка добавления
> plugin service и выбор узлов Network Graph пока не подключены к главному рабочему пространству. Создание сервиса выполняется
> через `POST /topology/services` или соответствующий Wails binding. Не путайте эту модель с полностью доступной вкладкой
> **Providers** для agent resources.

Плагин исполняется с правами admin и не изолирован. Устанавливайте только доверенные исполняемые файлы и ограничьте доступ к
каталогу plugins.

## Метрики и задержка туннелей

В **Manage panel → Metrics** есть диапазоны 1h/3h/6h/24h/all и две вкладки:

- **System** — CPU, память и сеть хоста;
- **Peers** — online-состояние, rx+tx активность и sparkline каждого пира.

Системные метрики агент собирает каждые 45 секунд по умолчанию (`VPN_AGENT_METRICS_INTERVAL`) и хранит до 48 часов с checkpoint
на диск. AWG-провайдер отдельно собирает rx/tx/handshake пиров (`VPN_PROVIDER_AWG_METRICS_INTERVAL`). Их API не объединены:

```text
GET /metrics                         система, также поддерживает ?fmt=prom
GET /metrics/history                 история системы
GET /metrics/{interface}             интерфейс и пиры
GET /metrics/{interface}/history     история интерфейса
```

Агент выполняет ICMP-пробы до `probeAddress` tunnel peers, хранит успешные RTT за 15 минут и вычисляет **p95**. До восьми проб
выполняются параллельно, таймаут одной — 2 секунды. Admin запрашивает метрики разных исходных серверов параллельно, а frontend
обновляет их отдельно от основного графа.

Цвет стрелки на Map:

- **синий** — p95 отсутствует или ≤100 мс;
- **жёлтый** — p95 >100 и ≤250 мс;
- **красный** — p95 >250 мс.

Tooltip стрелки показывает маршрут и числовой p95. Отсутствие ICMP-ответа не создаёт искусственно большую задержку: такая проба
просто не попадает в percentile.

API мониторинга и профилирования сохранены (`PATCH /servers/:id/monitoring`, `PATCH /servers/:id/profiling`,
`GET /servers/:id/profile`), но прежние переключатели из v1 не входят в текущий Manage panel.

## Настройки, безопасность и резервные копии

**Settings** содержит:

- English/Русский;
- **Backup** в обоих режимах;
- просмотр, экспорт и debug logging только в desktop;
- Basic Auth, смену учётных данных и logout только в standalone;
- версию приложения.

Basic Auth — дополнительный барьер поверх login session с той же учётной записью; по умолчанию выключен. Для публичного
standalone используйте HTTPS, смените admin/admin и при необходимости ограничьте доступ reverse proxy/firewall.

**Backup** экспортирует всю BoltDB: серверы, SSH/mTLS секреты, пользователей и пиров, topology/services/connections,
resources/links, OCI registry credentials и admin password hash. Храните JSON как секрет.

Восстановление выполняется при остановленном приложении:

```sh
./build/bin/awg-migrate export --db ~/.vpn-admin/db --out dump.json
./build/bin/awg-migrate import --db ~/.vpn-admin/db --in dump.json
```

Создайте отдельную копию целевой базы перед import. Не восстанавливайте файл под работающим процессом.

## Миграция с v1

Схема не мигрируется автоматически при запуске. Остановите v1 и создайте новую базу:

```sh
make migrate
./build/bin/awg-migrate v2 --db ~/.awg-admin --out ~/.vpn-admin/db
```

Источник открывается read-only, результат записывается атомарно. Существующая цель заменяется только с `--force`.

После запуска v2 перенесённые серверы и интерфейсы видны в Map/Graph со статусом **Unmanaged**. Для каждого сервера установите
v2 agent, затем AWG provider. При проверке статуса admin передаёт мигрированные resources и links провайдеру; unmanaged снимается
только после успешного принятия. Исходная база `~/.awg-admin` не меняется и служит откатом.

Полные гарантии, состав преобразования, случай уже существующей v2-базы и порядок отката: [docs/migrate_v2.md](migrate_v2.md).

## HTTP API

Standalone routes перечислены в `internal/api/handler.go`; desktop вызывает тот же service layer через Wails bindings. Основные
группы:

| Группа | Назначение |
|---|---|
| `/auth/*`, `/backup`, `/version` | Сессия, учётные данные, Basic Auth, экспорт и версия. |
| `/topology/*` | Servers/interfaces/services/plugin users/connections/positions/plugins/tunnel metrics. |
| `/servers/*` | Agent inventory, SSH/TLS, deployment, sync, metrics, interfaces. |
| `/servers/:id/providers/*` | Manifest, schemas, resources, status и actions. |
| `/links/*` | Provider links: list/create/apply/move/delete. |
| `/artifacts/*`, `/registry-sources/*` | OCI tags, provider catalog и сохранённые registry. |
| `/users/*` | Глобальные пользователи и AWG-пиры. |
| `/tunnels/*` | Совместимость со старой двухузловой моделью; для новых маршрутов используйте Graph/links. |

Все операционные routes, кроме login/logout, требуют standalone session. Перемещение использует `PUT /links/:linkID` и
`PUT /topology/connections/:connectionID`; создание plugin service — `POST /topology/services`.

## Диагностика

- **Сервер жёлтый на карте, но SSH работает.** Проверьте, что агент запущен, AWG provider виден в `/v1/manifest`, а мигрированные
  ресурсы вышли из Pending/Unmanaged.
- **Нет координат.** Проверьте Location и `locationError`. Если город отсутствует в Atlas, очистите Location и задайте обе
  координаты вручную. При недоступной сети используется ранее сохранённый `datacenter-atlas.json`.
- **Нет списка провайдеров из частного registry.** Проверьте `_catalog`, учётные данные и prefix. Либо введите provider/repository
  вручную; список тегов всё равно требует OCI `/tags/list`.
- **Pack отклоняет SSH.** Нужен ключ; для non-root — passwordless sudo. Парольный SSH сам по себе недостаточен.
- **Resource Degraded.** Откройте condition message и проверьте provider generation, логи `vpn-agent` и совместимость AWG kernel
  module. Желаемое состояние сохраняется для повторного reconcile.
- **Link Degraded после перемещения.** Проверьте ошибку на обеих нодах. Cleanup/rollback — best-effort; при сообщении об ошибке
  отката проверьте peers/hooks прежнего и replacement links перед повторной операцией.
- **Стрелка синяя без p95.** Это отсутствие успешных ICMP-проб, а не гарантированно нулевая задержка. Проверьте `probeAddress`,
  ICMP и включённый мониторинг.
- **Нужны подробные логи desktop.** Settings → Logs → Debug, воспроизведите операцию, затем сохраните JSON. В standalone смотрите
  stdout/stderr процесса и журналы агента на хосте.
